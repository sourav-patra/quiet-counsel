quiet-counsel

Reads an agent project's repository, works out what kind of project it is, flags what looks wrong, and shows the file and line, or the command, behind each number.

v0.1.0 · MIT · Python 3.11 or newer, standard library · no network call, no model

Install and run

pip install "git+https://github.com/sourav-patra/quiet-counsel@v0.1.0"
quiet-counsel classify ./project
quiet-counsel screen ./submissions/* --corpus ./corpus --out ./cards
quiet-counsel dashboard ./cards/*.json --out cohort.html

It runs locally on the Python standard library (3.11 or newer). It makes no network call and calls no model. The result is one HTML page you can open, email or commit.

quiet-counsel sample <dir> writes a synthetic project with five planted problems, and examples/sample-dashboard.html is the page built from it.

To check the no-network claim, run cases G-03 (no module imports a network library) and G-09 (a screen with every socket refused gives the same card byte for byte, with the clock fixed):

TZ=UTC PYTHONPATH=src:tests python3 -m unittest discover -s tests -t tests -k test_G03 -k test_G09

The same card has a secret-in-tree flag. A line that holds a credential shape, or a word such as secret, token or password, is not quoted by the scanner: the flag keeps its file and line (scripts/deploy.sh:2) and its quoted text reads [aws-access-key] <line withheld>. You open the line to read it. Every other line is quoted as written. A repository written to defeat this can still get text onto a card, so read a card before you share it.

quiet-counsel dashboard ./scards/*.json --out sample.html
sample.html: 1 project(s), 21,088 bytes

The dashboard page says: “Bands order attention, they do not rank quality, and nothing here is eliminated by a band. Every number below was produced by a command that is printed beside it, and every flag names its evidence (a file and line, or a command or commit), so you can check any claim on this page against the repository it describes.” The same page built from this sample is examples/sample-dashboard.html.

What it cannot see

It reads files in one directory tree. It cannot see stolen accounts, package registries, extension marketplaces, runtime behaviour or deployed versions. It does not run a project's tests, does not guess whether a person or a model wrote the code, and lists licence text without ruling on it in law. Copy detection matches identical content against the corpus you supply and misses a rewritten copy.

docs/NOTICES.md records eight 2026 incident patterns and what this tool does and does not look at for each. Of the seven that are not the hackerbot-claw campaign, five (the OpenAI and Hugging Face breach, the LiteLLM 1.107.0 release, the Cursor extension, the PHP flaw and the Node.js flaw) are marked invisible: the affected material is not in a repository tree, or depends on a version the tool does not compare against an advisory.

For the other two, the keyv worm and the fake audit workflow, the files appear with the compromise, so a screen of the affected repository had nothing to find beforehand; the checks can list them afterwards, to help a person triage. No detection rate exists for any of them.

What is measured, and what is not

  • Flags about a file cite its path and line. Flags about history or a missing file cite a command or a commit. tools/check_evidence.py confirms that each cited line exists and either holds the quoted text or is a line the scanner withholds (the excerpt reads <line withheld>: the line holds a credential shape or a word such as token, and you open it to read it). On this repository's own tree it reports 3 flags, all 3 citing a file and line (13 evidence items: 7 with the quoted text on the line, 6 withheld lines, 0 broken, 0 differing). Of the 24 numeric signals on a card, 0 cite a file and line; the rest cite the command that produces them. Reproduce with python3 tools/check_evidence.py . --list.
  • Accuracy is not measured and no benchmark exists. Case F-01 in docs/test-suite.md stays open until a person has read every flag from a real cohort.
  • Field run: one run by the author on 2 November 2026, of 50 public agent repositories drawn from a personal catalogue of agent tools, ordered by a hash of each name, taking the top 50 of that order under 150 MB, screened with this version's checks. There were 0 screen errors and 5 warnings from the checks added for the incident notices (4 install-time-script, 1 open-time-hook). In all, 4 critical, 31 serious, 36 warning and 34 information flags. The data-out and untrusted-code checks raised nothing, so the one place they have fired is test fixtures. The repository list is withheld so as not to name other people's projects, so a reader cannot reproduce this run; the aggregates are in docs/field-run-2026-11-02.json. No person has read every flag.
  • A project's own .scanignore can lower secret-in-tree and some other critical flags to information. They stay listed, --no-ignore restores them, and the verdict command still counts a flag lowered this way at its original severity.

Every flag is a finding for a person to rule on. The tool orders projects and cites evidence. It disqualifies nobody, and a high score does not mean a project is safe or that an agent will do better in it.

How it differs, by what each one needs

This tool reads one repository, or a hundred, without running anything, and reports what the files contain and the file and line, command or commit behind each number. The projects below answer nearby questions, and what each one needs in order to run is the place to start comparing. The table gives requirements as each project's page states them. It compares no accuracy and gives no ranking.

This tool reads a repository with scripts alone and cites what it finds. We read its README and design notes on 2 November 2026 and have not run it, so no comparison of results exists.

For the security of a single skill or agent configuration, use a dedicated scanner: the safety sweep here is a coarse pass across many projects and goes nowhere near that depth. For supply-chain practice in general, use OpenSSF Scorecard. To find out whether a project's code works, run its tests; nothing here runs them.
