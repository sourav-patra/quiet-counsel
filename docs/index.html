quiet-counsel

Hand it a repository. It runs nothing from it, sends nothing anywhere, and gives you flags with the file and line, command or commit behind each one.

The problem

Before you open someone else's agent project, ask what already runs by itself when you do.

Agent setups are mostly text and small scripts: instructions, skills, hooks, workflow files. A repository can ask your editor or agent to run a command the moment you open the folder. It can ask a package manager to run a script at install. It can hold a key someone pasted by accident, or a sentence written for whoever is judging it.

Published 2026 incident reports describe patterns like these:

  • Commands that run when a folder opens, and install-time package scripts.
  • A workflow step that sends secrets or history to a bare web address.
  • Pull request content run with secrets or agent write access.
  • A published package version replaced by a compromised release.

Reading every file by hand does not scale to a hundred submissions or a vendor's whole setup, and running the project to find out is the risk you are trying to avoid. quiet-counsel reads the files, runs nothing from them, and hands you a short list of places to look. What it cannot see says which of these patterns it can list and which it cannot.

The big picture

Everything happens on one machine, on the Python standard library: no network call, no model, no agent run. Package registries, accounts and runtime behaviour sit outside what it sees.

Scripts flag and a person rules. The band orders your attention (blocked, review, shortlist, screened) and disqualifies nobody.

How it works

Seven steps. With JavaScript on, choose a step to read about it. Without it, all seven are listed below.

    1. 1. Repository on disk

      Module: scan.walk, scan.git

      The tool opens the folder you point it at and reads files, plus a few read-only git queries such as the commit history. Nothing in the folder is executed, no install script runs and no network is used.

      Why it matters: Reading a file is not running it. A hostile project can only put text in front of the tool.

    2. 2. Classify

      Module: scan.classify

      It decides what kind of project this is (a skill catalogue, a harness, an application and so on) from the files present, not from the name, and lists the evidence for that choice.

      Why it matters: Different kinds of project get different expectations, so a tool repository is not judged as a catalogue.

    3. 3. Scan

      Module: scan.screen, checks.py

      It looks for patterns: credential shapes, commands piped into a shell, hooks that run on open, hidden characters, text aimed at an evaluator, licence conflicts, stated counts in the README that the files contradict, and claims it cannot support such as SOC 2. Each hit becomes a flag with a file and line, or a command or commit, and a severity, except unsupported claims, which are recorded as claims with status unsupported and are not flags.

      Why it matters: Every flag points at something you can open and read.

    4. 4. Withholding rule

      Module: scan.clip, scan.redact_all

      If a line holds a credential shape, or a word such as token, secret or password, the flag keeps the file and line but the quoted text reads <line withheld>.

      Why it matters: The card never repeats a secret it found, so you can share it more safely. A credential in a format the tool does not list can still get through.

    5. 5. Scorecard JSON

      Module: schema.py

      Flags, numeric signals and a band (blocked, review, shortlist or screened) are written as a JSON file. The score fields stay empty in screen mode.

      Why it matters: The data is the product. Other scripts can read it, and the dashboard step uses nothing else.

    6. 6. Dashboard HTML

      Module: dashboard.py

      One self-contained page lists every project with its band and flags. All project text is escaped, and each number has the command that produced it printed beside it.

      Why it matters: One file you can open, email or commit, with no server.

    7. 7. A person rules

      Module: you

      You read each flag, open the line, and decide. The tool orders attention and disqualifies nobody.

      Why it matters: A band says nothing about safety or about how well an agent performs.

      Does it work? Not measured

      • Flags about a file cite its path and line. Flags about history or a missing file cite a command or a commit. tools/check_evidence.py confirms that each cited line exists and either holds the quoted text or is a line the scanner withholds (the excerpt reads <line withheld>: the line holds a credential shape or a word such as token, and you open it to read it). On this repository's own tree it reports 3 flags, all 3 citing a file and line (9 evidence items: 5 with the quoted text on the line, 4 withheld lines, 0 broken, 0 differing). Of the 22 numeric signals on a card, 0 cite a file and line; the rest cite the command that produces them. Reproduce with python3 tools/check_evidence.py . --list.
      • Accuracy is not measured and no benchmark exists. Case F-01 in docs/test-suite.md stays open until a person has read every flag from a real cohort.
      • Field run: one run by the author on 2 November 2026, of 50 public agent repositories drawn from a personal catalogue of agent tools, ordered by a hash of each name, taking the top 50 of that order under 150 MB, screened with this version's checks. There were 0 screen errors and 5 warnings from the checks added for the incident notices (4 install-time-script, 1 open-time-hook). In all, 4 critical, 31 serious, 36 warning and 34 information flags. The data-out and untrusted-code checks raised nothing, so the one place they have fired is test fixtures. The repository list is withheld so as not to name other people's projects, so a reader cannot reproduce this run; the aggregates are in docs/field-run-2026-11-02.json. No person has read every flag.
      • A project's own .scanignore changes no flag, cap or band unless the person screening passes --honour-ignore for that one project; when the file holds a usable pattern the card reports the file, its path-shaped patterns and how many files they match. Under that option the file can lower secret-in-tree and some other critical flags to information, and a project can lower its band. They stay listed, and the verdict command still counts a flag lowered this way at its original severity. --no-ignore is accepted and does nothing.

      Every flag is a finding for a person to rule on. The tool orders projects and cites evidence. It disqualifies nobody, and a high score does not mean a project is safe or that an agent will do better in it.

      What it cannot see

      It reads files in one directory tree. It cannot see stolen accounts, package registries, extension marketplaces, runtime behaviour or deployed versions. It does not run a project's tests, does not guess whether a person or a model wrote the code, and lists licence text without ruling on it in law. Copy detection matches identical content against the corpus you supply and misses a rewritten copy.

      docs/NOTICES.md records eight 2026 incident patterns and what this tool does and does not look at for each. Of the seven that are not the hackerbot-claw campaign, five (the OpenAI and Hugging Face breach, the LiteLLM 1.107.0 release, the Cursor extension, the PHP flaw and the Node.js flaw) are marked invisible: the affected material is not in a repository tree, or depends on a version the tool does not compare against an advisory.

      For the other two, the keyv worm and the fake audit workflow, the files appear with the compromise, so a screen of the affected repository had nothing to find beforehand; the checks can list them afterwards, to help a person triage. No detection rate exists for any of them.

      Google's Elephant-Goldfish Model has fresh-context subagents review a design before code is written, and its drift report compares checked-in documents with source code; it runs inside a coding agent. This tool reads a repository with scripts alone and cites what it finds. On 2 November 2026 the author also ran its drift report once on a small made-up project with six planted README contradictions. The drift report found all six and also flagged the one true claim as differing in contract. This tool found none, since it checks only stated counts and figures (tests, skills, coverage, speed-up) and a short list of claims it cannot support, such as SOC 2 or production-ready. The drift report used a model and about 238,000 tokens; this tool used neither. One sample measures no accuracy. The author did not run its review pipeline. Results from one sample do not make a comparison.

      For the security of a single skill or agent configuration, use a dedicated scanner: the safety sweep here is a coarse pass across many projects and goes nowhere near that depth. For supply-chain practice in general, use OpenSSF Scorecard. To find out whether a project's code works, run its tests; nothing here runs them. The full comparison, including what was and was not checked, is in docs/COMPARISON.md.

      Install and run it

      pip install "git+https://github.com/sourav-patra/quiet-counsel@v0.1.0"
quiet-counsel sample ./sample
quiet-counsel screen ./sample --out ./cards
quiet-counsel dashboard ./cards/*.json --out cohort.html

      Other install forms (pipx, uv, from source, Windows, upgrade, uninstall) are in docs/INSTALL.md, and a GitHub Actions snippet is in docs/CI.md.

      It runs locally on the Python standard library (3.11 or newer). It makes no network call and calls no model. The result is one HTML page you can open, email or commit.

      quiet-counsel sample <dir> writes a synthetic project with five planted problems, and examples/sample-dashboard.html is the page built from it.

      To check the no-network claim, run cases G-03 (no module imports a network library) and G-09 (a screen with every socket refused gives the same card byte for byte, with the clock fixed):

      TZ=UTC PYTHONPATH=src:tests python3 -m unittest discover -s tests -t tests -k test_G03 -k test_G09
