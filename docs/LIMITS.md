# What is enforced, what is not, and what it cannot see

## What is enforced now and what is not

- Accuracy on real repositories is not measured. A benchmark exists on author-built fixtures ([BENCHMARK.md](BENCHMARK.md)) and says nothing about how often these problems occur in real repositories. Case F-01 in [test-suite.md](test-suite.md) stays open until a person has read every flag from a real cohort.
- Flags about a file cite its path and line. Flags about history or a missing file cite a command or a commit. `tools/check_evidence.py` confirms that each cited line exists and either holds the quoted text or is a line the scanner withholds. On this repository's own tree it reports 3 flags, all 3 citing a file and line (9 evidence items: 6 with the quoted text on the line, 3 withheld lines, 0 broken, 0 differing). Of the 22 numeric signals on a card, 0 cite a file and line; the rest cite the command that produces them. Reproduce with `python3 tools/check_evidence.py . --list`.
- Field run: one run by the author on 2 November 2026, of 50 public agent repositories drawn from a personal catalogue of agent tools, ordered by a hash of each name, taking the top 50 of that order under 150 MB, screened with this version's checks. There were 0 screen errors and 5 warnings from the checks added for the incident notices (4 `install-time-script`, 1 `open-time-hook`). In all, 4 critical, 31 serious, 36 warning and 34 information flags. The data-out and untrusted-code checks raised nothing, so the one place they have fired is test fixtures. The repository list is withheld so as not to name other people's projects, so a reader cannot reproduce this run; the aggregates are in [field-run-2026-11-02.json](field-run-2026-11-02.json). No person has read every flag.
- A project's own `.scanignore` changes no flag, cap or band unless the person screening passes `--honour-ignore` for one project. The card reports the file, its patterns and the number of files they match (case I-26). Under `--honour-ignore` a project can lower its band: the file can lower `secret-in-tree` and some other critical flags to information, they stay listed, and the `verdict` command still counts them at their original severity. `--no-ignore` is accepted and does nothing. The file is read as data and refused when it is a symlink.
- A check that stops at a hit, copy or file budget has not read the rest of the tree. The card then carries a limits entry naming the check and its budget and a `scan-limit-reached` warning, and the band is at least `review`. This reports the limit and does not close it: a credential, licence line or copy past a budget stays unread, and any file can fill a budget, with or without a `.scanignore` (case I-32). Checks that only feed a count or an information flag get a limits entry and no `scan-limit-reached` flag and no band change: untrusted-content guidance (6), machine-specific paths (10), the case-only evaluator listing, and the README flag check, eval evidence and result figure reads. The root `.scanignore` is not read by any check, so it uses none of these budgets (case I-26).
- Licence, claim and README checks read what the project wrote, with or without a `.scanignore`. Adding a `COPYING` file moved a tree from blocked to screened, and renaming a README to `README.aaa` moved one from review to screened, both measured with no `.scanignore`; neither is part of the promise above.
- An SPDX line gets the label of every family any of its identifiers names, so `MIT OR GPL-3.0` is reported as GPL: the check reads names and a person reads the choice. `WITH` exception names and `LicenseRef-` names get no label.
- Hidden directories other than `.github` are not read by the credential, evaluator-text, hidden-character, installer, licence and copy checks, so content placed in `.cache/` or `.private/` is not seen by them. `.git` is never read. The skill, agent, command and host-configuration inventories read every hidden directory, and so do the README flag check (source files) and the eval evidence check, which are information only. Those walks still skip `SKIP_DIRS` such as `.cache` and `.venv`. Other hidden directories, including `.git-extra`, are outside the security checks: a credential or evaluator phrase placed there is not seen.
- The test-path rule is by name: a directory called `test`, `tests`, `testdata`, `fixtures` or `__tests__`, or a file named `test_*` or `*_test.*`, so a production file called `src/test_runtime.py` counts as a test path.
- The tool screens itself in its own test suite (case H-16) and must raise no critical or serious flag against its own tree.

## README claims that are checked

`readme-claim-mismatch` (information, no cap) compares four kinds of README statement with the files: a licence name against the root licence file, "no dependencies" or "standard library only" against the manifests, a `--flag` against the source files, and a backticked path in a sentence that says the repository includes it. A flag is checked only when it is written in a code span that starts with the project's own command (a `pyproject.toml` script, a `package.json` bin, or the folder name); a bare flag, another tool's flag and a list entry that links elsewhere are not checked. Command files, `SKILL.md` and scripts with a shebang line count as files that can hold a flag name. Paths in negated sentences, sentences addressed to the reader's own project, and owner/repo or model-id shaped tokens are skipped. Wording such as "keep scripts dependency-free" is an instruction and is not checked. It stays quiet when the README is scoped, when the licence is dual or not identified, and for generated or ignored paths. The author ran the first version on 50 repositories (the tuning set) and one AI agent ruled its 21 statements: 1 true, 19 false, 1 unclear. The checks were then tightened and run once on 50 other repositories, which gave 2 flags (the score flag covers 2 README lines and the mismatch flag 1 line): the agent that did not build the checks ruled one flag true and one false. Two flags are too few to state a rate (the aggregates are in [field-run-2026-11-03.json](field-run-2026-11-03.json)), and recall (what the checks miss) is not measured. On a small planted tool whose README writes its flags without the command, 3 of 6 planted README claims are found (licence, dependencies, a missing folder); a flag written with the command is found as well. Because no kind reached 5 decided statements, both checks report at information, carry no cap and cannot change a band. Retry counts, network use and every other kind of README statement are not checked. Others check flags and paths too; the part added here is that the evidence cites both the README line and the file or its absence. A flag counts as present when its literal text, or its quoted name, appears in a source file, so a framework that derives flags from field names can still raise a false mismatch.

## Eval evidence

The signal `eval_evidence` keeps three states apart. `setup` means a config or decorator that shows evals are set up (`evals/evals.json`, `promptfooconfig.yaml`, an Inspect `@task`, the OpenAI registry, lm-evaluation-harness tasks, `@pytest.mark.langsmith`). `result` means a file a run writes (an Agent Skills `iteration-*/benchmark.json` or `grading.json`, an Inspect `logs/*.eval`, DeepEval `.deepeval/` or `test_run_*.json`, an eval folder's `results.json`). A recognised result file name is possible evidence that a run happened; nothing reads the file's contents or its history, so an empty `evals/results.json` also reads as `result`, and it does not show that a README number matches. `score-without-result` (information, no cap) fires when the README quotes a score, ranking or benchmark comparison and the state is not `result`. Results kept by a hosted service (LangSmith, Braintrust, Ragas) leave no file, so the flag says the result may be kept elsewhere and never calls a claim false. Only the layouts above are matched; a project that names its eval files otherwise reads as `none`. The wordings matched are a percentage near a benchmark name, "beats" a named product, a ranking with a score, "N% fewer", and "state of the art" or SoTA beside a benchmark name. Vaguer wordings ("higher performance", "Top 20", "best") are not matched. A README figure that a JSON, CSV or Markdown file under `docs/`, `benchmarks/` or `results/` holds clears the flag. It reports at information. On the 50 fresh repositories it raised 1 flag (covering 2 README lines), ruled true, which is too few to state a rate; recall is not measured.

## What it cannot see

It reads files in one directory tree. It cannot see stolen accounts, package registries, extension marketplaces, runtime behaviour or deployed versions. It does not run a project's tests, does not guess whether a person or a model wrote the code, and lists licence text without ruling on it in law. Copy detection matches identical content against the corpus you supply and misses a rewritten copy. Text addressed to the evaluator is reported and never acted on, and a determined author can still write the surrounding words on purpose.

[NOTICES.md](NOTICES.md) records eight 2026 incident patterns and what this tool does and does not look at for each. Of the seven that are not the hackerbot-claw campaign, five (the OpenAI and Hugging Face breach, the LiteLLM 1.107.0 release, the Cursor extension, the PHP flaw and the Node.js flaw) are marked `invisible`: the affected material is not in a repository tree, or depends on a version the tool does not compare against an advisory. For the other two, the keyv worm and the fake audit workflow, the files appear with the compromise, so a screen of the affected repository had nothing to find beforehand; the checks can list them afterwards, to help a person triage. No detection rate exists for any of them.

## Credentials in cards

A scorecard withholds a line that holds a credential shape or a word such as `token`, but a credential in a format the tool does not list can still appear, so read a card before you share it. The rules and their limits are in [SECURITY.md](../SECURITY.md), which also says how to report a problem.
